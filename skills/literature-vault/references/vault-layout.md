# Vault layout, frontmatter and tag taxonomy

The house shape shared by the literature vaults in this user's Obsidian vault. Match it unless the user asks for
something else.

## Directory layout

```
<vault>/knowledge/<vault-slug>/
  README.md      entry point: what the vault is, conventions, scope, copyright, what it is NOT
  MOC.md         Map of Content — the hub; every note reachable from here
  MAP.md         comparative map of the sources, chapter interleave, where they diverge
  TOPICS.md      the same vault sliced by tag/theme (generated)
  GLOSSARY.md    core hand-written definitions + machine-merged full roster
  sources/       one bibliographic note per source
  chapters/<source-slug>/   one note per chapter, in the source's own order
  <subject-dir>/ one canonical note per subject, all sources merged
  concepts/      the reusable vocabulary
  indexes/       correspondence and lookup tables (generated)
```

Keep it flat enough to browse: two levels under the vault slug, three at most.

## Why `chapters/` and `<subject-dir>/` both exist

They answer different questions and both are wanted:

- `chapters/` = what **one source says**, in **that source's order**. Faithful to the document, including its
  quirks — a printed contents that puts Chapter 11 between 3 and 4 keeps that order, and the vault says why.
- `<subject-dir>/` = what **all sources together say** about one subject. Merged, deduplicated, and explicit about
  divergence.

When a merged note and a chapter note disagree, the merged note names which source says what.

## Frontmatter schema

Key order is fixed; the generated indexes parse these keys.

```yaml
---
type: Chapter | <Subject> | Concept | Glossary | Index | Source | Book
title: "Human readable title"
aliases: []
source: <source-slug> | both
author: <author>
book_year: <year>
pages: "40-62"                      # or "2009: 77-92; 2003: 107-115" when merged
tags: [source/<vault-slug>, book/<source-slug>, <domain>, theme/<theme>, status/draft]
concepts: [<slug>, <slug>]
up: "[[knowledge/<vault-slug>/MOC]]"
status: draft
generated:
  by: process:<vault-slug>-vault
  at: <YYYY-MM-DD>
---
```

`source:` and `book_year:` are what let a generated index group notes by book without re-reading prose.

## Tag taxonomy

Closed families, 2–5 tags per note:

| Family | Purpose | Rule |
|---|---|---|
| `source/<vault-slug>` | this vault | mandatory on **every** note; the verification script checks it |
| `book/<source-slug>` | which source the note rests on | plus `book/both` for merged notes |
| domain tags | subject matter, single words | closed set fixed in the contract (e.g. `kabbalah`, `chakra-system`, `kundalini`, `taoism`) |
| `theme/<theme>` | the **kind** of content, for cross-source slicing | closed set (e.g. `theme/energy-anatomy`, `theme/ethics`, `theme/practice`, `theme/correspondence-table`) |
| `status/draft` | working notes | on every note until the user says otherwise |

A closed set matters: `TOPICS.md` lists one section per tag, so an open vocabulary produces a tag index with
60 sections of one note each. Keep the sets small and reuse them.

## Glossary: the two-part split

A machine-merged glossary alone reads like a word list; a hand-written one alone never covers what the chapters
defined. Publish both in one file:

1. **Core terms** — ~40–60 entries written by the parent, grouped by area (the system / the anatomy / the
   doctrine / the path), each a short definition in the source's sense plus a link to the note that develops it.
2. **Complete roster** — every term from every note's `## Terms introduced` table, de-duplicated, senses joined
   with `·`, pushed through an alphabetical `### A…Z` layout, with the notes each term came from.

State the counts in both (`N terms in the roster`, `N + N = total`) — it is the only way to notice a wave whose
terms failed to merge.

## MOC: the hub

The MOC is curated, not generated. It carries:

- a short abstract of the whole system in a handful of sentences;
- a "start here" table mapping reader intents to notes;
- the source table with imprint and ISBN;
- the subject table (one row per subject, the key attribute of each — the spine of the vault);
- the chapter lists per source, **in the source's own order**;
- the concept vocabulary grouped by area;
- the index table;
- a "read this responsibly" block: study summary, claims-as-claims, no medical advice, practice described not
  taught, rights holder named.

## Generators vs hand-writing

| Hand-written by the parent | Generated by script |
|---|---|
| README, MOC, MAP | TOPICS, FULL-LIST, cross-source correspondence tables |
| source notes, glossary core table | glossary roster, per-chapter counts |
| index *prose* ("notes on the table") | index *tables* |

Generated notes still need their frontmatter written into the template by hand — the script only fills the body.
